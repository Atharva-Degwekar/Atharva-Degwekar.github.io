RUNBOOK · AGENT-MIGRATION-01 FOR: DEVELOPERS ON LARGE, ONGOING PROJECTS

Codex → Claude Code
Migration Runbook

How to move an ongoing, large project from Codex to Claude Code without losing context, without surprise commits, and without burning tokens re-explaining the codebase every session.

01 / CHALLENGES

What actually goes wrong when you switch

These are the failure modes teams hit most often moving a live, non-trivial codebase from Codex to Claude Code — and the specific habit that avoids each one.

A

Codex's accumulated context doesn't come with you

Every decision, workaround, and "why we did it this way" that lived in your Codex conversation history stays in Codex. Claude Code starts cold on session one.

Fix — Before switching, ask Codex/ChatGPT for a written handoff summary (purpose, architecture, decisions, open issues). Feed that into Claude Code's first read-only session so it verifies the summary against the real repo instead of guessing. See the companion prompt file.
B

No shared persistent-memory file yet

Codex workflows often lean on conversation history for continuity. Claude Code's equivalent is a project-root CLAUDE.md file it reads at the start of every session — if it doesn't exist, Claude re-derives context (and burns tokens) each time.

Fix — Run the pre-work context-capture prompt once to generate a durable context.md, and keep a short CLAUDE.md pointing to it plus your house rules (style, test command, guardrails).
C

Different default autonomy / permission model

Approval settings, sandboxing, and what counts as a "safe" auto-run action differ between the two tools. A permission that felt safe in Codex can mean something more permissive in Claude Code, or vice versa.

Fix — Don't assume defaults carry over. Explicitly set your permission mode and, separately, state your git rules in plain language every session (see Guardrails, below) rather than trusting a tool-level setting alone.
D

Risk of silent large-scope edits on a big repo

On a large project, an agent that's uncertain about scope can "helpfully" touch more files than intended — renames, reformatting, or reorganizing that mixes with your real change and makes review hard.

Fix — Start every new task by asking Claude Code to state its plan and the exact file list it intends to touch before it edits anything. Review the list first.
E

Auto-commit / auto-merge habits carrying over

If your Codex setup allowed git actions automatically, that habit is easy to assume is fine here too — and a wrong assumption on a shared branch is expensive.

Fix — Bake an explicit "always ask before commit/merge/push" rule into CLAUDE.md and repeat it in-session on anything touching shared branches. Treat it as non-negotiable, not a default you inherited.
F

Team prompting habits don't transfer 1:1

Prompt phrasing that worked well in Codex (structure, verbosity, how you specify constraints) isn't guaranteed to produce the same behavior in Claude Code.

Fix — Give the first few sessions a short adjustment period. Keep tasks scoped and check the plan/diff before accepting, rather than assuming identical phrasing means identical results.
G

Re-reading the whole repo every session wastes tokens

Without a persistent context file, a large codebase means every session pays the "figure out the codebase" cost again in input tokens.

Fix — This is what context.md and CLAUDE.md solve structurally — see Section 03.
02 / PRE-WORK

Run the context-capture prompt first

Before any real task, run Claude Code once in read-only mode to build its own map of the project and write it to context.md. The full copy-paste prompt, plus instructions for pulling a handoff brief out of Codex/ChatGPT first, is in the companion file:

claude-code-context-capture-prompt.md

In short, that prompt tells Claude Code to:

  • Treat this as a context-gathering session only — no edits outside context.md.
  • Read the repo (code, README, commit history, comments) and, if you provide it, a pasted Codex/ChatGPT handoff summary — verifying that summary against the real code rather than trusting it blindly.
  • Write a structured record: project summary, architecture, tech stack, repo layout, conventions, current in-progress work, and an explicit list of open questions it couldn't resolve on its own.
  • Report back in chat what it found and what's still unclear — not just "done."
03 / GUARDRAILS

Rules to set every session, not just once

Set these explicitly in CLAUDE.md so they persist, and restate the git rule verbally in-session for anything touching a shared branch — a tool-level permission is not the same as a standing instruction it will re-check every time.

Non-negotiable, every session

  • Never run git commit, git merge, or git push without asking first and getting an explicit yes — even on tasks where it technically has the access to do so.
  • Never touch a file outside the stated scope of the current task without flagging it and asking.
  • During context-gathering sessions: read-only. The only file it may create or edit is context.md.
  • State the plan and file list before editing anything on a new task.
  • Keep context.md updated as work happens, but never by silently deleting prior sections — call out what changed and why.
04 / TOKEN EFFICIENCY

Get good output for fewer tokens

Most of the token cost on a large project is re-explaining context and re-reading files the agent already saw. These habits attack that directly.

01

Keep CLAUDE.md short and pointed

A few hundred words: what the project is, where to find context.md, your house rules, your test/build commands. Claude Code reads this every session — a bloated file is a recurring tax.

02

Let context.md replace re-exploration

Once it exists, point new sessions at it instead of letting the agent re-grep the whole repo from scratch. Update it incrementally rather than regenerating it.

03

Scope tasks narrowly

"Fix the pagination bug in OrderListView" costs far fewer tokens than "look through the order system and fix what's wrong" — the second forces broad exploration every time.

04

Clear or compact context between unrelated tasks

Long-running sessions that drift across unrelated tasks accumulate irrelevant history that gets re-sent with every turn. Start a fresh session per task where the tasks aren't related.

05

Use prompt caching for repeated context

Content that's identical across calls (a large CLAUDE.md, a pasted spec) is far cheaper to re-send as a cache read than as fresh input — this matters most on long sessions with heavy shared context.

06

Match the model to the task (see Section 05)

Route routine, mechanical work to a cheaper/faster model and reserve the most capable model for genuinely hard reasoning or large multi-file changes.

05 / MODEL CHOICE

Which model, and why

As of September 2026, four Claude models are current. Pricing is per million tokens (input / output) and changes over time — confirm current rates at docs.claude.com before relying on exact figures.

ModelBest forContext windowToken behavior
Haiku 4.5 Fast, mechanical work: simple edits, formatting, quick lookups, high-volume/low-complexity subtasks. 200K tokens Cheapest per token; no adaptive "thinking" step, so latency and cost stay low and predictable.
Sonnet 5 The default for most day-to-day Claude Code work — everyday features, refactors, bug fixes on a large codebase. 1M tokens Adaptive thinking with adjustable effort — dial effort down for routine tasks to cut both latency and token spend.
Opus 5 Complex, multi-file agentic coding, architecture-level decisions, and the hardest debugging on a large project. 1M tokens Highest capability, priced accordingly — reserve for tasks where Sonnet's output quality genuinely isn't enough.
Fable 5.1 The most demanding reasoning work, where the capability gain justifies a real cost premium over Opus. 1M tokens Adaptive thinking is always on; priced above Opus — use selectively, not as a default driver.

A practical routing rule

Default new sessions to Sonnet 5 for general Claude Code work. Drop to Haiku 4.5 for batch-style mechanical subtasks (renames, boilerplate, simple lookups) via subagents where your workflow supports it. Escalate to Opus 5 only when Sonnet's plan or output is visibly insufficient — a hard architectural call, a gnarly multi-file bug, a large-scope refactor. Treat Fable 5.1 as a deliberate, occasional choice rather than a default.

06 / HANDOFF

Instructions to give Codex or ChatGPT

If Codex/ChatGPT has been carrying this project's context, run this in Codex/ChatGPT before your first Claude Code session, and paste the result into the companion prompt file's handoff placeholder:

Summarize everything you know about this project for a handoff to another
AI coding assistant: project purpose, architecture, tech stack, key
decisions and why they were made, current in-progress work, known issues,
and anything unusual or non-obvious about the codebase. Write it as plain
prose/bullets I can paste elsewhere — don't assume the reader has this
conversation's history.

Claude Code then treats that summary as a hypothesis to verify against the real repository — not as ground truth — and records any mismatches it finds in context.md.
